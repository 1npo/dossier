# Prompt: plan the package refactor (paste into a fresh Opus session)

You are planning, not building. Write an implementation plan to reorganize the `dossier` skill repository so that (a) all programmatic code and the data it consumes become a properly architected, documented Python package, and (b) the non-code content (the files Claude and humans read) is laid out so a person can understand the skill at a glance. A different, less capable model (Sonnet) will carry out your plan one task at a time, so the plan must be explicit enough to follow without design judgment. Do not modify any file except the plan you write. Do not run `/dossier build` against any repository, and do not install tools or run restores. Reading files, running the default test suite, `git`, and `gh api` are fine.

## Where things are

- The repository and skill root: `/home/nick/dev/projects/dossier` (call it `SKILL`). It is the only copy you may read as the source of truth. It is also installed through the plugin marketplace (`.claude-plugin/`), so never read or edit an installed copy under `~/.claude/plugins` or `~/.claude/skills`.
- How work is organised, and the model for the plan's shape (task format, phasing, verification blocks, "Results" discipline): `SKILL/docs/process.md` and the most recent finished plans in `SKILL/docs/plans/` (`012-m6-plan.md`, `013-post-v1-plan.md`). Reuse their conventions. Name your plan with the next free number in `docs/plans/`.
- Conventions you must follow and cite: load the `py-projects`, `py-unit-tests`, `docs-project`, `docs-readme`, `docs-user-guide`, `docs-dev-guide`, `git-workflow` and `claude-planning-docs` skills before planning, and obey them.
- Run `git log --oneline -15` and `git status` first. Record the default and slow test baselines (pass, fail, skip counts and wall time) at the commit you plan from. Known failures on `main` must be listed by name. The slow suite must run with `--basetemp` under `~/.cache`, never `/tmp`.

## The problem

1. `SKILL/scripts/` holds about 90 flat Python modules (`adapters.py`, `cs_*.py`, `js_*.py`, `py_*.py`, `measured_*.py`, `checks_*.py`, `render.py`, `dossier.py` the CLI, and so on), plus Node helper folders (`scripts/node/`), worker scripts with `.lock` files, and a data file (`eol.json`). Language adapters, measurement, checks, rendering, process orchestration and CLI are all mixed together at one level, with prefix naming standing in for packages.
2. `SKILL/tests/` is a large flat set of test modules under `unit/`, with `integration/`, `tools/` (ad hoc scripts such as `ground_truth.py`, `layout_probe.py`, `m3_page.py`), fixtures, `conftest.py` and a `scip_fake.py` helper.
3. The rest of the repository (`SKILL.md`, `README.md`, `prompts/`, `rules/`, `assets/`, `vendor/`, `docs/` with plans, prompts, scratch and reference, `VERSION`, `.claude-plugin/`, `.github/`) has grown by accretion. It is hard for a human to tell which files are the skill's instructions to Claude, which are data consumed by the Python code, which are shipped static assets, and which are project history.

## Requirements (the human's, not negotiable)

- **The repository stays the skill root.** A user must still be able to install the skill by cloning the repository into `~/.claude/skills/dossier`, and by the plugin marketplace. `SKILL.md` stays at the root with its frontmatter. Anything `SKILL.md` or the prompts tell Claude to run must still work from `${CLAUDE_SKILL_DIR}` after a plain clone, with no `pip install` step by the user. Work out and state how the package is found and run: for example `uv run` against a `pyproject.toml` at the root with a `src/` layout, a thin launcher script, or `uv run --project`; compare at least two options, recommend one with the reason, and verify the recommendation by reading how `SKILL.md` invokes the CLI today (`uv run ${CLAUDE_SKILL_DIR}/scripts/dossier.py`) and how the PEP 723 inline-dependency headers, the worker `.lock` files and the Node helpers are resolved today. Say what happens to each.
- **A proper packaged Python library.** Propose the package name, `src/` layout, the subpackage tree and the dependency direction between subpackages. Use real abstractions where the code today repeats a shape across languages (the Python, JS/TS and C# adapters each have `*_adapter`, `*_api`, `*_entries`, `*_project`, `*_queries`, `*_tools` modules; there are `measured_*` and `checks_*` families). Read the code to find the actual common interface before proposing one: define the adapter protocol or base class, a registry, and what is shared, from evidence. Do not invent abstractions the code does not need; say what you chose not to abstract and why.
- **Consumed data lives with the package.** Everything primarily read by the Python code (rule files under `rules/`, `prompts/schema/*.json`, `eol.json`, `assets/` templates, CSS and JS, `vendor/` bundles, Node helper projects) must be classified: package data (moves under the package and is loaded through `importlib.resources`, with no `__file__`-relative path hacks), or skill-root content that stays. For each file group, give the decision and the reason. Files that Claude is told to read directly by `SKILL.md` (for example `prompts/method.md`, `prompts/reports.md`) are read by path from the skill root: keep them reachable, and say whether the Python code also reads them.
- **Architecture and documentation.** The plan must specify module docstrings, public API (`__all__`) per subpackage, type hints, and a developer-guide architecture section with a dependency diagram, per `docs-dev-guide`. State the ruff and type-check settings to adopt (check what `pyproject.toml`, if any, already has) and what is out of scope.
- **Tests mirror the package.** `tests/` becomes a tree that mirrors the package's subpackages, with fixtures, `conftest.py` and helpers placed by what uses them. Ad hoc scripts in `tests/tools/` are either promoted to real dev tooling inside the package or a `tools/` folder with a stated owner, or deleted with a reason. Keep the default and slow suite split and the markers as they are unless you justify a change.
- **The non-code content becomes legible.** Propose the top-level layout for a human reader: what the root contains and why (`SKILL.md`, `README.md`, `LICENSE`, `VERSION`, `pyproject.toml`, `.claude-plugin/`, `.github/`, the package, the tests, `docs/`, and one home each for prompts, rules and assets). Decide where `docs/plans`, `docs/prompts`, `docs/scratch`, `docs/reference` and `post-v1.md` belong (history and working material must not crowd the reader-facing docs; keep or archive, never silently delete: say which and why, and look at `claude-planning-docs` for where planning files go). Each folder gets a short README or docstring that says what is in it and who reads it. Include a "map of the repository" section for the README.
- **Behaviour must not change.** This is a refactor. Dossier output must be byte-identical before and after for the same input. The plan must define how that is proven: the Python, TS/JS and C# golden runs, the default and slow suites, and a before/after comparison of a built dossier's `facts.json`, `summary.json` and HTML (name the fixture repositories and where they come from; read `docs/plans/012-m6-plan.md` and `013-post-v1-plan.md` for how earlier milestones did this). Any intended behaviour change is out of scope and goes in a "left out" list.

## What the plan must contain

1. **Inventory.** A table of every file and folder at the repository root and every module in `scripts/` and `tests/` with its current role, size, importers (use `grep`, or a small throwaway script run from your scratch folder, never inside the repository), and its destination in the new layout. This is the heart of the plan: Sonnet moves files by this table. Group by subpackage where that keeps it readable, but cover every file.
2. **The target architecture.** The tree, the subpackage responsibilities, the dependency rules (what may import what, with the cycles you found today and how to break them), the adapter abstraction, the CLI entry (command parsing split from command implementations), the package-data loading approach, and the public API.
3. **How it is found and run** after a clone (see Requirements), including every place that hard-codes a `scripts/` path: `SKILL.md`, `README.md`, prompts, the agent definitions, the GitHub workflow, the incremental rebuild's version stamps, the "skill: <commit> (clean|dirty)" line in `doctor`, `process.md`, and anything in `docs/`. Produce a grep-derived list.
4. **Phases and tasks.** Order the work so the suite is green after every phase and each phase is one reviewable commit: for example (a) add packaging and the launcher, no moves; (b) move data and make loading go through `importlib.resources`; (c) move leaf modules, then adapters, then the core, one subpackage per task, using `git mv` so history follows; (d) the CLI split; (e) tests tree; (f) abstractions that need real code changes; (g) top-level and docs reorganization; (h) docs and architecture write-up. Each task states: the exact files moved or edited, the import rewrites, the command that proves it, and the expected output. Mark which tasks need Opus judgment and which are mechanical for Sonnet, and propose the realistic count of each. Include a rollback note per phase.
5. **Verification blocks.** The exact commands, run by Claude and not the human, that prove: clean-clone install into a scratch `HOME`-like location works; `doctor`, `version`, `check` and `build` (on a small fixture repository, never on the human's repositories) run through the documented entry; byte-identical output before and after; default and slow suites pass with the recorded baselines; ruff and the type check pass; no stale `scripts/` path remains in any doc; the plugin marketplace layout still resolves (read `.claude-plugin/` and say what, if anything, changes).
6. **Risks and open questions.** Things that can break silently: `${CLAUDE_SKILL_DIR}` resolution, PEP 723 headers, the `.lock` files, Node helper paths, vendored bundle paths in the generated HTML, the history tests that read git history (`fetch-depth: 0`), the `skill:` commit line, `incremental.py` stamping module versions, `__pycache__` committed or ignored, executable bits. For each give the default you chose; the author's rule is to take the sensible default, say which, and not make the rest of the plan wait for a ruling.
7. **Spec issues and left out.** Anything you found that is wrong or ambiguous in current docs, plus the deliberately deferred ideas (for the `post-v1.md` backlog; do not edit it).
8. **Release.** Say whether this is a version bump (it changes install layout, so propose the bump level with the reason, following `git-release` and `py-projects`) and what the CI workflow needs changed.

## Output

Write the plan to `docs/plans/<next-number>-package-refactor-plan.md` (and nothing else). End your reply with the path, the number of phases and tasks, the Opus/Sonnet split, and the three decisions you most want the human to look at.
